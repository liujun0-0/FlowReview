# 变更评审报告

让评审者先理解完整业务流程，再沿“业务步骤 → 实现方法 → 实际 diff”理解改动，区分必要性、实现风险和验证结果。先呈现可疑改动、未知项及覆盖缺口，再分配精力。

## 默认交付：新版浏览器阅读器

“生成报告 / 出 review 文件 / 评审这次改动”默认执行：生成 review.json → 用本 skill 的 scripts/open_reader.py --build-only 采集新快照 → 检查业务链路与方法定位缺口 → 用 --snapshot 启动本地阅读服务 → 交付实际输出的 http://127.0.0.1:端口/review/... 地址。仅生成 JSON、review.html 或给出 file:/// 链接不算完成默认报告交付。只有用户明确要求单文件 HTML/离线旧版，才使用旧版渲染器并传 --legacy-html。

读取本 skill 或启动脚本遇到“拒绝访问”时，先区分权限与文件不存在，使用环境允许的授权读取或修复安装后重试；无法访问则报告阻塞，不改用 Downloads、备份目录里的同名旧 skill，也不退回 HTML。

执行脚本使用本 SKILL.md 所在目录的绝对路径，不要把 scripts 当成业务仓库目录。报告包含完整业务图 journey、实现 hops 和关系证据；不要为绕过采集错误而删掉这些数据。阅读器缺失/未构建/启动失败时修复可处理的问题，否则如实说明阻塞和已保存的 JSON，不自动改交旧版 HTML。用户只要摘要时按摘要范围交付，无需启动服务。

这是结构化自审，使用作者上下文时应说明来源。用户已授权独立审查时，可由独立上下文核对代码和需求，再与作者解释比较；不因本 skill 默认创建会话或子代理。右侧追问也不等于独立审查。

阅读器按功能分区，选中功能默认显示它自己的全链路画布（入口 → 各项目业务步骤 → 最终结果）。展开项目后显示方法总框、内部步骤及调用连线；方法流程画布已融入该层，不再单列入口。可切换“沿链阅读”或“业务步骤图”。底层使用本地 React Flow + ELK，支持拖动、缩放、缩略图和右侧源码。对象引用线按对象增删改着色，虚线仍表示引用依据边界；展开项目保留缩放，框内非交互区域可拖动。入口变化依据匹配到的 HTTP 接口方法，不把新增下游步骤当成新增入口。入口/结果可在右侧查看示例，采集格式见 references/report-format.md。沿用现有 JSON 与固定快照；不要生成手工 HTML/SVG 来替代默认阅读器。流程引用要求见 references/method-sequence.md。

## 1. 确定基准与范围

优先使用当前对话的修改说明、需求文档或 PR 描述。Commit message 仅为意图线索，不能自动充当完整验收标准。缺少影响判断的依据时，提出具体问题，同时继续收集机械 diff；依据不足标“待确认”，不要用实现反推需求。

明确项目、仓库及比较模式，不能把包含多个项目的工作区目录当成所有服务共享的 Git 根目录：

- `worktree`：基点（默认 HEAD）到工作区，包含暂存、未暂存、未跟踪文件，排除 Git ignore 文件。输出放仓库外，避免报告进入自己的审查范围。
- `commit`：单个提交与父提交比较；合并提交改用 range 显式选择基点。
- `range`：两个版本树直接比较，对应 `base..head`。
- `branch`：merge-base 到目标分支，对应 `base...head`，通常用于 PR。

跨项目必须配置 `repositories` 并为 hop/orphan 填 `project`。渲染器解析版本 SHA 并保存 diff SHA256；工作区证据是导出的代码与指纹，仅凭 HEAD 不能重建脏工作区。

## 2. 先还原业务流程，再嵌入变更

先确定数据源、触发者、入口（HTTP 方法与应用内 URL / 路由 / 页面事件）、输入、业务目的和结果出口。阅读基准版本与当前实现，沿入口追到业务层、数据层和下游调用，保留完成这项功能所需的未改步骤；机械 diff 清单可先收集，但不能以变更方法清单代替业务骨架。

以“校验导入文件”“保存待处理任务”等业务动作组织步骤，方法名是实现位置。一个业务步骤可关联多个真实方法，一个方法也可参与多个步骤；方法级调用关系作为下钻视图。逐跳说明用途、所属层次、输入输出、主要过程、分支与异常、数据表和下游接口，并给源码证据。只补齐与该功能结果有关的依赖，不扩展成全系统全量分析。

遇到异步任务/MQ，核对生产方、持久化或消息载体、触发/扫描/消费方、分派规则、关键状态转换及结果回传；不能把“保存任务”直接连成“调用执行方法”。事务、重试、补偿、部分成功等依据实际实现解释，未核实的外部调度配置/消费者/库表写明边界。静态读码不能当作端到端运行通过。

业务图的变化类型独立于源码方法的增删：抽取新方法不自动成为新增业务动作；已有步骤改为调用共用实现时标“实现调整”，说明预期保持的行为和待验证项。逐步骤比较前后逻辑，再标出第一处变化、变化原因和传播到的后续步骤。未改的主干、原有分支与结果必须保留，未追清的部分标待核对，不能声称全链路完整。

同一功能含多个接口时，保持一个 flowPoint，使用 `journey.entries` 逐接口记录入口方法锚点、用途、参数和结果；各入口向下追踪，公共方法复用同一 hop，不能把多个 URL 拼成一个入口或复制整个功能分区。字段与兼容说明见 [report-format.md](references/report-format.md#同功能多接口入口36)。

每个功能点单独填写 `journey`，不能把多个功能的链路混成一个全局图。`journey.steps[].project` 与 `repositories` / hops 的项目标识一致；一个步骤横跨多个项目时，按实际责任边界拆步并核对边界两端。除 source、steps 外，还要核实并填写 `journey.links`，显式连接主路径、分支、失败出口及异步交接；有步骤无连线不能认定完整，仅靠方法 links 不能补齐业务连线。未核实的边界保留 coverage.boundaries / unknowns，按部分交付，不为消除警告猜箭头。浏览器报告用功能点的 `journey` 保存业务图，字段见格式参考；`chains/hops/links` 保存可定位的实现及方法关系。不能只写一段总说明后继续把变更列表画成业务流程。

### 2.1 收集变更并核对覆盖

先用 `git status --short`、diff 文件清单与统计建立完整变更目录，再按文件或功能分批核对全部原始 diff；`-w` 只作辅助降噪，不能作为唯一输入，空白可能影响字符串、YAML、Python 等行为；未跟踪项也要纳入目录。

拆分变更原子，记录文件、行号、函数、类型和对应需求。类型：`新增 / 删除 / 改签名 / 改实现 / 传播变更 / 契约变更 / 穿越未改`。

双向映射：每条需求是否实现；每处改动是否属于需求。没有归属的列入 `orphans`，不要自动当成错误或直接删除。

渲染器单独生成机械覆盖清单：实际 diff 的 hunk 是否至少展示一次。未展示 hunk、二进制、权限变化、空文件等保留为缺口。非文本项需单独核对时可以放入 `exclusions`，写具体原因；不能为通过校验排除漏审内容。

**已展示不代表已审查，明确排除不代表安全。**

### 2.2 按需取码与复用（保留完整审查效果）

节省重复输入，不削减审查范围、链路证据和必要上下文：

- **先完整业务骨架，再定点取码**：使用精确符号和少量上下文的 diff 定位，读取入口、关键未改步骤及变更所属完整方法和相关字段、注解、类配置。长方法可分段读，但判断前补齐影响该改动的分支、状态和异常处理。只有局部信息不足，或变化横跨类结构/初始化/配置时，才读完整文件。不得将 diff 的上下文行数当成分析边界。
- **未改代码按问题扩展**：围绕“输入从哪来、走哪个分支、数据如何传递、最终影响什么、失败如何处理”检索。普通工具/框架调用先查签名和契约；若结论依赖实现、默认值、类型转换、权限、事务、并发或副作用，就读实现。入口、跨服务/异步边界及关键副作用须有证据；结论所需信息已闭合后停止无关扩展，不设固定调用深度或取码行数上限。未解决的问题保留 unknowns，不能以省 token 为由标为确定。
- **按真实方法去重**：本轮记录已核对的仓库、版本/工作区内容指纹、文件、侧、方法签名与位置，以及结论、证据和待确认问题。多个功能链复用同一方法的事实与源码，不重复读取；仍分别核对各入口的参数、前置条件及副作用。相同名称不代表相同方法，不跨项目、重载或新旧版本混用。
- **更新时检查失效**：再次生成先核对范围、SHA 与相关工作区文件指纹。源码、需求或关联契约发生变化时，重读受影响的方法及依赖其假设的上下游；只有证据仍有效才复用原结论。不能仅按 HEAD 未变认定工作区未变，也不能机械继承“看过/通过”。没有可靠指纹时重新核对，增量分析不能漏掉删除、重命名、配置、未跟踪文件或受影响的未改路径。
- **覆盖完整，深度按风险**：变更目录中的每处变化均须核对归属和影响，不因略读、折叠、生成文件或没有功能链归属而跳过。未深入分析、明确排除及无法解析的内容如实列出；字段、配置、测试和契约变更不能自动判低风险。节省的是重复源码与无关延伸，不是必要验证。
- **源码交给本地工具保存**：Git/浏览器模式只输出定位、解释和证据，默认不填 JSON 的 code、不让模型复述完整新旧源码，也不把生成的 HTML、manifest 或 sources 全量读回。脚本可直接执行；正常成功只读统计，失败再查相关诊断。浏览器只验证必要交互和局部界面；查业务逻辑优先精确读取源码。用户主动展开完整文件仍由本地读取，不触发 AI。
- **说明只写有效差别**：功能点 before/after 解释完整流程；节点 role/why/behavior 解释本处用途、理由和实际变化。共享方法复用已核实事实，避免逐行重复同一段长解释，但每个节点保留格式必填字段、可独立理解的理由及链路特有风险。当前格式不支持的引用字段不要自行发明。只读本次需要的格式参考，不默认加载离线示例或脚本实现。

## 3. 检索调用链与风险分档

从精确符号用代码检索、LSP 或 codegraph 核实调用关系。记录入口、跨服务边界、终点副作用，以及依赖被改动假设的未修改节点。

- 已核实：`confidence: 确定`，`evidence` 写实际源码位置、检查结果；计划执行的命令不是证据。
- 无法确认的动态派发或仓库外调用：`confidence: 猜`，写清所需证据，链路名不能把推测伪装成事实。
- `穿越未改` 展示指定侧的源码上下文，禁止用附近 diff 冒充该节点变化。

`tier` 取 `略读 / 细看`，按实际行为风险分档。测试、配置、字段映射、签名跟随不能默认略读；删断言、权限配置、金额映射、序列化变化等应细看。略读项在 `risk_detail` 说明低风险依据。待确认或未分类项不能默认隐藏。

细看项填写 `focus`：`算法 / 状态流转 / 并发 / 事务 / 错误处理 / 边界`，可多选。

## 4. 评估必要性与验证

细看项说明方法整体作用 `role`、为什么改 `why`、不改会怎样 `counterfactual`，给 `verdict`：

- `必要改动`：实现需求需要，不表示实现正确或可以合并。
- `优化型改动`：有收益但并非必需。
- `非必要改动`：缺少本次范围内必要性。
- `疑似误改`：有触发条件或反证，需核实。
- `待确认`：证据不足，必填 `assessmentReason`。

按需补 `necessity`（必要/可选/非必要）、`match`（匹配/部分匹配/不匹配/看不出）、`reasonableness`（合理/勉强合理/不合理）。不要硬凑结论；`穿越未改` 不强制价值判断。

`risk_detail` 写具体风险或已核对边界与残余限制，允许“当前证据未发现具体缺陷”。`unknowns` 可为空，只记真实未决项，不强制制造疑问。

`verify` 是计划；`verifyStatus` 默认 `未执行`，还可取 `通过 / 失败 / 受阻`。通过或失败时必填 `verifyResult` 和 `verifyEvidence`（实际命令、退出码、日志或测试产物位置）。渲染器不保证人工填写的结果真实。

Git 实际增删行之和 ≥400 或文件数 ≥15 时必须给 `verifyPlan`，小改动高风险也应给。选择适用的表征、性质、差分、契约测试；影子运行只写建议，不擅自执行线上操作。验收同时覆盖预期新行为、保留行为及失败边界，不能一律要求新旧等价。

## 5. 输出与校验

生成 JSON 时读 [references/report-format.md](references/report-format.md)。[examples/review.example.json](examples/review.example.json) 是自带代码的离线示例。

默认使用本地浏览器阅读器的全链路画布：每个功能先显示入口、项目业务步骤、变化起点和最终结果，项目展开后按实际调用布置方法/对象框，方法总框内展示过程与调用。点击方法标题打开完整方法，点击内部调用打开目标方法，右侧先解释功能与变化再显示源码/差异；修改方法默认前后对比。接口示例必须按入口归属采集：有 journey.entries 时逐项填写 entries[].requestExamples / responseExamples；只有单一旧入口时才写 source。每个接口的请求和响应各提供至少一份有依据示例，或在同一项的 exampleGaps.request / response 写明未能采集的具体原因，区分异步提交响应、最终结果与失败示例；无资料时明确缺失，不强行补造响应包装。保留沿链阅读和业务步骤图选项。业务链路先核对完整，再按方法粒度采集实现；不能因为界面换了就沿用只有类级位置的旧数据。

本 skill 随 FlowReview 项目分发。首次在 FlowReview 根目录执行 `npm ci` 和 `npm run build`（Windows 也可用 setup-review.cmd）；之后按需启动，不需要每次安装，也不依赖 CDN。仓库内版本自动定位配套阅读器，安装版本通过安装脚本记录的本地位置查找；部署说明见项目 docs/getting-started.md：

```powershell
python scripts/open_reader.py review.json --out 新快照目录 --build-only
python scripts/check_sequence.py 新快照目录/manifest.json --strict --require-business-flow
python scripts/open_reader.py --snapshot 新快照目录
python scripts/open_reader.py --stop
```

工具位置优先用 `--tool-dir`，其次用 `FLOWREVIEW_HOME`（兼容 `YADIFF_REVIEW_HOME`）指定。安装后搬动项目需重新运行安装脚本 --update，不能猜测工具安装路径。阅读器只监听本机；复用已有服务，无页面心跳五分钟退出。阅读标记与疑问独立保存在用户目录，源码快照不会随工作区后续改动改变。重新生成的不同快照不自动继承旧结论。

JSON 必须指定各项目 `repositories` 和比较范围。生成时核对范围仍然对应本次说明：若改动已经提交，不能继续把旧说明与 `HEAD → 工作区` 当成同一次差异。不得擅自改用推测的基准。已有报告没有版本证据时明确提示说明尚需与当前源码核对。

每条功能链优先填写通俗的 `before`（原有流程）和 `after`（本次改变），说明输入、分支、结果和失败路径。节点说明写在实际变化附近；`why` 解释业务理由，`role` 解释方法整体用途，`behavior` 写前后差别。避免“穿越未改”等内部术语，界面显示“原有代码”。不要把文件罗列冒充直接调用链。

方法点击目前在已采集的源码中查找同名定义，展示类和签名候选，不能把同名匹配当作已确认调用。跨服务、动态分派和快照外定义仍须检索核实。未归入功能链的实际变更保留在文件列表，不能当作已审查。默认收起原有代码、类级和零散上下文，按需展开。

完成浏览器交付前核对：命令退出成功且输出实际访问地址；有条件时确认左侧按功能分区、默认全链路画布包含本功能的入口/项目步骤/结果，展开项目后有方法框及步骤调用，点击框/内部调用能打开对应源码侧栏，并能切换沿链阅读。无法检查页面时如实说明。最终交付包含地址、快照路径和采集警告；服务地址中的凭证以本次实际输出为准，不复用过期链接。可在报告旁保存启动入口，调用 open_reader.py --snapshot 的绝对路径以便服务退出后重新打开。

原 JSON 的解释与新采集源码不一致、缺少版本证据或工作区发生变化时必须保留警告；转换报告不等于重新完成评审。

仅旧版 HTML 或结构/覆盖校验需要时读 [references/legacy-html.md](references/legacy-html.md)，默认生成流程不读取或执行旧版 HTML 示例。

### 全链路画布与方法流程的数据要求

默认全链路画布先按项目汇总本功能的业务步骤，项目展开后显示方法与对象。业务步骤及步骤连线写 journey.steps / journey.links，真实实现写 chains/hops，方法关系写 chain.links；二者必须对应，不能用 journey 的一段总说明代替实现方法。按入口到结果的可理解阅读顺序组织 hops，顺序仅辅助阅读，不代表耗时或动态执行时序。分支、循环、异步交接在 process、branches、links.label 中明确说明。

- **方法必须定位进真实方法体**：每个相关执行方法单独一个 hop，填真实 project/file/func/side 和该侧方法声明或方法体中的准确行号。不要把类声明、注入字段、注释或空行作为方法定位。同一个类内的关键调用也要拆出目标 hop，重载核对签名和调用参数；新旧侧不能混用。新类不能只采集一个类级 hop 来代表全部方法。保留对理解功能必需的未改方法，不无限展开无关工具调用。
- **总框写清被调用的方法**：未改方法主要写 role 与简短 process；修改/新增方法必填 role、process、branches、behavior、why。process 使用“获取锁 → 读取配置 → for 每项【分页循环【调用 Class.method(主要参数) → 校验 → 写入】】 → 返回结果 → finally 释放锁”这样的有序短文字；以 →、->、；或换行分步骤，以成对【】表达循环/分支/事务块嵌套。格式只用于组织已核实步骤，不据此推断真实调用或耗时，包含本次增加或调整的关键方法调用名称、输入输出、影响的分支及失败后果；只写“新增校验/组装数据”或重复 role 标题不够；尤其不能把多层循环、锁和 finally 压成一个功能名。无额外分支时如实说明，不填占位词或复述整个方法源码。
- **框内调用可钻取**：关键调用的方法名应直接出现在相应 process 步骤中，优先写 Class.method(参数) 或方法引用 ::method；连线从该步骤出发，不在方法底部重复整份调用列表。同名/重载无法唯一匹配的关系仍保留待核对入口，不按名字强行连线。关键调用补齐调用方和目标方法的 hops，填本链 links 的 from/to、label、confidence、evidence。evidence 写调用方该版本的准确调用行、目标类/方法、参数或契约匹配依据。确定且有证据才为实线；同名检索只提供候选位置。普通调用、条件调用、循环、Feign/HTTP、异步交接分清类型；不能将先后步骤、对象使用、接口实现关系一概标成直接调用。
- **区分方法变化与调用边变化**：新增目标方法不自动证明调用边新增；根据新旧调用方核对增加/删除/调整的具体调用，在 caller.behavior/process 与 link.label 写清，例如“新增调用 Foo.validate；校验失败不保存”。调用原有方法时，目标仍是原有方法。当前阅读器没有独立调用边变化字段，禁止自行发明 calls/sequenceSteps/changeKind 等未支持结构。
- **对象连到使用点**：新增/修改 DO、DTO、VO、请求响应对象保留独立 hop，写明字段变化、类型/默认值/必填与兼容影响、生产方和消费方。首次构造/读取/映射所在的方法也要采集，在方法 process 和对象 role/evidence 写出方法及准确行号。当前工具只对同项目、无歧义的快照内类型名做词法挂接，位置不等于语义绑定或运行时首次使用；对象以独立变更框展示，通过引用虚线连到首次词法出现的方法；跨项目或未能挂接的对象如实单列，不能写成工具已确认连线。不支持的 objectRefs/firstUse 字段不要生成。
- **入口和跨应用边界**：接口方法填 endpoint 的 HTTP method、应用内 path、源码证据；网关前缀未知就不补。Feign、MQ、调度任务核对两端、传递对象和状态/结果反馈。框内未改过程简写，影响判断所需的边界证据不能省略。

首次/更新生成应读 [references/method-sequence.md](references/method-sequence.md)，按已有字段填写。生成快照后运行 scripts/check_sequence.py 快照目录/manifest.json --strict --require-business-flow（新生成报告；使用本 skill 绝对路径），仅输出局部诊断，不全量读源码快照。修正关键方法定位和缺少的方法说明，再重新生成新目录；无法修正则保留原因并以“部分”交付，不能声称已完成完整功能链路。纯转换旧报告只运行 --strict（不加 --require-business-flow），保留原有业务缺口警告，不擅自重新评审，也不能通过删掉未定位节点规避提示。

当前工具支持方法框点击打开完整方法、框内关系点击目标源码，方法自身变化颜色由新旧源码采集核对。原有业务图支持适配、缩放和拖动，全链路画布支持项目展开/收起、空白平移、节点拖动、缩放、自动排列、已展开方法定位与专注模式；不要混淆两种视图能力。代码内同名定义候选不是 IDEA 级引用分析。旧报告缺字段或只有类级采集时明确提示，不能自动补造过程。

### 沿链阅读与新增文件

新增类/文件按文件展示一份完整源码，在对应方法或变化行旁分别放说明；不能为每个方法重复展示整个新增文件。节点定位、阅读标记与疑问仍独立保存。链路摘要交代起点、处理阶段和最终影响；方法步骤显示项目、类、作用及变化类型，数据结构、字段和类级上下文归入辅助节点，不混作执行步骤。

功能链 name 用通俗阶段名组织，保留真实分支及跨服务/异步边界，不把任意节点列表写成直接调用。报告 hops 若只是关联阅读顺序，应明确说明；只有源码/检索证据充分时才称为实际执行或调用关系，不能靠画箭头补足缺失证据。未来更新报告时核对并整理调用关系，避免继续沿用杂乱的文件顺序。

### 测试代码的展示

单元测试、集成测试、测试夹具和测试辅助文件显著标为“测试代码”，与业务实现分开讲解；不要把测试执行步骤混入生产调用链。浏览器的“隐藏测试代码”可过滤链路节点、文件及疑问列表，并显示隐藏数量；过滤只是阅读偏好，全部变化及疑问仍保留，可随时恢复。按测试目录和明确命名识别，不能仅凭名称含 Test 就认定业务类是测试。

测试节点说明优先概括覆盖的行为、关键断言变化及验证结果，避免逐行解释搭建数据、mock 等重复细节；删断言、跳过测试或改变契约的风险仍须核对。用户选择隐藏测试不等于已审查，也不代表可从变更覆盖中排除。

## 6. 阅读与继续审查

先看覆盖缺口、未知项，再看“可疑”（含待确认）及“需细看”。大改动结合行为验证计划；跨项目核对边界两端。右侧显示必要性、风险和验证状态，底部保留版本及机械覆盖证据。

按钮只生成供复制的上下文，不执行修改。修复前先核实问题；一致性修复需要上下游配套时，解释最小改动集合，不强制只改一个函数。CLI 包装依赖目标 shell，Windows 优先复制纯文本或存 `.md`。

回归测试：`python -B -m unittest discover -s scripts -p "test_*.py"`。仅创建清理临时 Git 仓库，无网络或 LLM 调用；可设 `REVIEW_TEST_TMP` 指定可写临时目录。

纯 POM 版本传播不作为业务执行链：保留 POM 路径与行号，阅读器从固定源码展示依赖/父模块/管理版本及修改。只有版本属性不能证明真实依赖；消费者的声明在子模块时应采集该 POM。多入口缺少方法边时明确说明缺口，不能把同功能下不同接口的入口和服务方法串成假调用链。

多 URL 入口必须逐个定位 Controller 方法并填写 journey.entries，不能用 `/page|filters|detail` 代替入口清单；核对 HTTP 动词、路径、请求/结果、实际被调方法。多入口视图逐方法独立展开；筛选某入口时不把其他入口专属方法显示为未关联节点。转换旧报告不能只换 UI 后宣称完成多入口采集。

结果缺失时阅读器可按固定源码返回类型/DTO 展示保守的字段形状占位示意，标明非实测、非完整 HTTP 响应，不代替报告的契约核对。Void 明确展示无业务返回体；异步入口不能套用后台 Service 的统计对象作接口响应。生成报告时核对 Controller 的实际返回表达式，再判断业务结果与统一包装。

阅读器的源码 DTO 示意支持嵌套对象、集合/数组、String 键 Map 和可解析的泛型父类。按当前引用路径检测自引用/互引用，默认最大 5 层、24 次类型解析、200 个字段，截断处显示 null 及原因；同类型的不同兄弟字段可分别展开。这仅是静态类型形状，不能当作完整序列化响应或已实测值。
